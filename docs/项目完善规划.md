## 二、现状评估：已完成 vs 待完善

### 2.1 已完成（核心链路）

- 关键词：增删改、分类、模板、JSON 导入导出、`lastScannedAt`
- 定时/手动扫描：可配置间隔 + `GET /api/scan/status` + 顶栏状态条
- **10 源聚合**：`aggregateSearch`（监控 + 搜索 Tab 共用；设置页开关）
- **平台发现**：5 平台纯榜单、快照、近 7 天刷新趋势、Top5 AI、洞察面板
- **搜索增强**：单平台 / 时间窗 / `sortBy`（`SearchOptionsPanel`）
- AI：OpenRouter 扩展、分析、发现洞察、无 Key 降级
- 热点雷达：筛选、趋势（按日）、报告导出、删除、详情抽屉
- 通知：WebSocket、站内、邮件、Webhook、每日日报
- 前端：`pages/*` 五 Tab + `AppContext` + 组件化
- 工程化：Vitest、Playwright E2E、CI、Docker、`npm run demo`
- Agent Skills + [SKILLS_VS_WEB.md](./SKILLS_VS_WEB.md)

### 2.2 待完善（与「完整项目」的差距）

| 维度 | 现状 | 剩余缺口 |
|------|------|----------|
| 发现页快照趋势 | 每次刷新一根柱 | 未按日聚合；同日多次刷新标签重复（体验可优化） |
| 发现洞察 | 需 ≥2 次快照 | 新用户需引导多刷新几次 |
| 平台发现源 | 5 平台 | Google/Bing 榜单模式仍不接入（设计取舍） |
| 多用户 | 单用户 SQLite | 登录/多租户 ⏸️ 按需 |
| 文档 | 三份用户向文档已对齐 | 大版本发版时同步 CHANGELOG + 截图 |

### 2.3 完善原则

1. **不盲目堆功能**：优先「文档承诺 = 代码行为」「API 已有 = UI 补上」。
2. **分阶段交付**：每阶段产出可演示版本。
3. **对齐 README 六大能力**：避免宣传与实现不一致。

## 三、规划框架：四个维度

把一个 side project 做成「能展示、能维护、能部署」的产品，通常补齐以下四块：

```
┌─────────────────────────────────────────────────────────┐
│  1. 产品完整度 — 功能闭环、体验一致                      │
├─────────────────────────────────────────────────────────┤
│  2. 工程结构   — 模块拆分、测试与 CI                     │
├─────────────────────────────────────────────────────────┤
│  3. 可观测运维 — 任务状态、日志、配置界面                │
├─────────────────────────────────────────────────────────┤
│  4. 对外呈现   — 文档、截图、一键启动/部署               │
└─────────────────────────────────────────────────────────┘
```

**推荐顺序：** 产品完整度 → 工程结构 → 可观测运维 → 对外呈现。
